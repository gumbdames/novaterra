# NOVATERRA — Internationalization (I18N)

## Current state: English-only

Per the 2026-09-30 user directive, the entire shipped game is in **English
and English ONLY** — no Hebrew or any other language's string data ships in
`src`, `index.html`, or the built bundle. This is enforced by
`game/tests/ui.i18n.test.ts`, which fails if any Hebrew Unicode (U+0590–U+05FF)
appears in shipped source.

## Where strings live

All player-facing copy lives in `game/src/ui/strings.ts` as the `STRINGS`
object, in two groups:

1. **Localized via `loc()` / `fillLoc()`** — the roster-expansion sections:
   `unitNames` (97), `buildingNames` (100), `unitTabs`, `buildingTabs`,
   `upgradeGroups`, `ageNames`, `upgrades` (21 names + one-line effects),
   `palettes` (tab titles, tools, placement hints, cost labels, lock
   reasons). Every entry is a `LocalizedString` and is read through the
   localization machinery (see below).
2. **Plain English strings** — the legacy Phase 1–3 sections: `menu`,
   `hud`, `selection`, `orders`, `advisor`, `pause`, `settings`, `help`,
   `save`, `cheats`, `end`. These were never localized; they are used
   directly (e.g. `STRINGS.hud.funds`) without `loc()`.

New UI copy should always be added as group 1 (`LocalizedString` entries
read via `loc()`/`fillLoc()`), so it is localizable from day one. Group 2
entries can be migrated into `LocalizedString`s opportunistically if a
second language ever ships.

## The localization machinery (`game/src/ui/strings.ts`)

The indirection is kept on purpose as the extension point:

- `LocalizedString` — `{ en: string }` today. A future locale adds its
  field here (e.g. `he: string`).
- `UiLanguage` — `'en'` today. A future locale extends the union
  (e.g. `'en' | 'he'`).
- `setUiLanguage(lang)` / `getUiLanguage()` — module-level language state.
- `loc(s)` — picks the current language's text via a `switch` on
  `uiLanguage`. A future locale adds a field to `LocalizedString` and a
  case here.
- `fill(template, vars)` / `fillLoc(template, vars)` — substitute
  `{placeholders}` in every shipped language; unknown placeholders are
  left as-is (loud, not silent).

The module is pure (no DOM, no three.js) and headless-safe under Node/vitest.

## How to add a future language

1. Add the locale's field to `LocalizedString` (e.g. `he: string`).
2. Extend the `UiLanguage` union (e.g. `'en' | 'he'`) and set the desired
   default.
3. Add a `case` for it in `loc()`, and extend `fill()` to substitute the
   new language.
4. Translate **every** entry in the group-1 sections of `STRINGS`
   (unitNames, buildingNames, unitTabs, buildingTabs, upgradeGroups,
   ageNames, upgrades, palettes). Optionally migrate group-2 sections
   into `LocalizedString`s and translate those too.
5. Update the tests: `game/tests/ui.palettes.test.ts` (name-coverage
   tests) and `game/tests/ui.i18n.test.ts` (the no-Hebrew smoke test
   assumes English-only; scope it to the languages that are NOT shipped,
   or drop it once a second language ships).

## How the (removed) language switcher worked

A language picker used to live in the Settings panel
(`SettingsPanel.show()` in `game/src/ui/menus.ts`): a `<select>` with one
option per `UiLanguage`, live-applied via `setUiLanguage()` (the HUD
rebuilds every tick, so the new language showed on the next repaint with
no reload) and persisted in `Settings` (`loadSettings`/`saveSettings`,
localStorage key `novaterra.settings.v1`). At boot, `game.ts` applied the
persisted choice with `setUiLanguage(saved.language)`.

To bring a switcher back: re-add the `<select>` in `SettingsPanel.show()`
(one `<option>` per locale), restore the `language` field on `Settings`,
and re-add the `setUiLanguage(saved.language)` call in the game
controller's boot path. The plumbing (`setUiLanguage` /
`getUiLanguage` / `loc` / `fillLoc`) is still there — only the UI for
choosing was removed.
